# Skills — free versus paid, and how to add one

**🚨 The brain is served by tier (2026-10-25, second-brain `plans/2026-10-25-slates-brain.md` step 4).** This public
repo keeps only the Director card and the router (`packages/shared/skills/slates-start-here.md`) and the partials
TypeScript reads (`PARTIALS`). Every playbook, rule and model guide, and the partials only they inject, live in the
private **`slates-api/brain/`**, and slates-api serves them by the account's tier (`brain/tiers.json`; who opens
which: `slates-api/src/lib/brain.ts`): a Slates license opens everything but the bump list, the Agentic Skills Pack
or the membership opens the bump list too. Only the brain Eric approved is served (`slates-api/brain-approved.json`
pins its commit and the approved brain hash; `brain-review.mjs --approve` moves both with the scoreboard's
`approvedCommit`, `approvedApiCommit` and `approvedBrainHash`, and slates-api's build stops when they disagree). **Never put a brain file back in this
repo or a plugin** (`build-plugins.mjs` refuses one).
- **Runtime:** `src/skills/served.ts`. `brainFiles()` is the card and router plus the served brain; the guide op,
  My brain, craft cards, banned tokens, the doctrine's guide index, the MCP prompts and `install-skills` all read it.
  Sources: `SLATES_BRAIN_DIR` (builds, checks, evals; never a user's machine) is the only one when set. Otherwise
  the process starts from `~/.slates/brain-cache.json` (written by this login, or by the desktop app when there is no
  login here; a cache another login received waits until the server names the same account), then `GET /brain` and
  `/brain/bundle` through the connected account replace it (at server start and before a guide answer, at most every
  ten minutes). The cache names the credential that fetched it; a 401 or 403, or a sign-out (`slates logout`, the
  desktop's), clears the brain and deletes the cache only when that login received it, so a revoked CLI key never
  takes a signed-in desktop's brain. A guide past the account's tier
  answers with the server's notice (a model guide's carries its craft card) and counts as read, so the job runs on
  the general rules; a guide not on the machine at all (nothing connected yet) does not count, and the gate's
  refusal says how to connect.
- **Builds, checks and evals** find the folder through `scripts/brain-source.mjs` (`SLATES_BRAIN_DIR`, which a
  worktree must set, else `../slates-api/brain`); single-repo CI has none and skips what reads it. The behaviour A/B
  fixture answers `/brain` and `/brain/bundle` from it with every tier open, so a candidate build fetches its brain
  the way a member's does; a served baseline needs `--baseline-brain`.
- **A brain edit is a slates-api commit.** `brain-lint.mjs` checks sources there since `brainSourcesSince`, and
  `brain-review.mjs` lists commits from both repos on Eric's page.

**⚠️ What follows predates the move:** read "packages/shared/skills/" as the brain's two homes (this folder for
the card and router, `slates-api/brain/` for the rest).

**⚠️ Who reads what is the tier map, not this file.** The card and router are public; a Slates license opens every
other brain file except the bump list; the Agentic Skills Pack or the membership opens the bump list too
(`slates-api/brain/tiers.json` names it and says why; `src/lib/brain.ts` maps each entitlement). A model guide is
never on the bump list: a license that can generate must be able to read the guide the gate requires. Moving a
file between tiers is an offer decision and Eric's. The pack's own skills (campaign blueprints harvested from our
real ads) live in `slates-api/pack-skills/`. Doctrine: `second-brain/business/projects/slates/strategy/funnel-architecture.md`
→ "Pack content doctrine" and `membership-model.md` §13.

**A skill's tier is the folder it lives in, and nothing else.** Free: `packages/shared/skills/` here. Paid: `slates-api/pack-skills/`, in the private API repo. The chart of every skill and its tier is generated by the pack build (`dist-pack/pack-manifest.json` → `catalog`) and rendered on slates.video/docs/skills-pack; nobody types a list of skills anywhere.

**🚨 Paid skills NEVER go in this repo.** It is public, and `packages/shared/package.json`'s `files`
array includes `skills`, so **that folder ships inside the public npm tarball**: anyone can
`npm pack @slatesvideo/shared` and read every file in it. An entitlement filter in `install-skills`
protects nothing; it is security by omission over a public artifact. **The only real gate is keeping the file out of public
distribution.** The two paid ad skills sat in this repo's `pack-skills/` from 2026-08-16 until
2026-09-27 and are still in its public git history (Eric chose not to rewrite it, 2026-09-22).

`scripts/embed-skills.mjs` globs `packages/shared/skills/*.md` only, so paid bodies never enter
the public `SKILLS` record or npm package. The slates-api `/members` feed serves both tiers to
entitled accounts, reading the paid folder directly. The shared prompting-guide operation discovers
entitled paid metadata and retrieves a requested private leaf through the connected cloud account;
the served brain stays available offline from the cache.

Two ad skills were written straight into `packages/shared/skills/` on 2026-08-16 and swept into a
release commit by a `git add -A`. They never reached npm (the build ran before the files landed),
but the near-miss is why this rule is now explicit. **Use explicit paths in `git add`, never `-A`.**

Build the pack with `npm run build:skills-pack` (root). It assembles the free skills plus
everything in `../slates-api/pack-skills/` (or `SLATES_PACK_SKILLS_DIR`) into a deterministic zip,
refuses to build when the paid folder is missing or empty or a key is in both, and generates the
README and the chart so the inventory is never hand-typed. After a rebuild, run
`node scripts/check-skills-pack-lockstep.mjs --write` in slates-web to refresh the site's chart. The zip's download URL is
hand-mirrored in **two** repos and gated by `slates-web/scripts/check-skills-pack-lockstep.mjs` —
**never move that URL before the object is uploaded**, or every paying customer gets a 404.

**The skills are one layered brain (2026-10-25; second-brain `plans/2026-10-25-slates-brain.md`).**
`slates-start-here` holds the Director card (between `@director` markers, extracted by
`src/prompts/brain.ts` into both surfaces' doctrine) and the router: one playbook per job, the method to
offer for each result (§ Offer the method that gets the result: Blender blocking for a choreographed
one-take, motion graphics for exact on-screen text, and the rest), and the rules they link. **A new
capability that beats a prompt for some result gets its line there**, or agents never offer it. Every
other file leads with an operative summary (`@operative` markers, two to seven bullets each ending on
`(§ heading)`), or its craft card on a model guide. `retrieveGuide` serves the router and every playbook whole
at its default depth (an agent follows a playbook's steps) and a rule or model guide at that summary or card. The
desktop doctrine carries the router whole; an MCP connection that has not opened it gets it once, with the
user's My brain preload in front, as its own content block on the first result of a tool that spends nothing
(`ROUTER_NOTICE`; never a billable op's result), and the router's own answer carries the preload itself, so
the MCP working method only points at it. `npm run check:brain` (in the build) holds the rest (`scripts/brain-lint.mjs`):
- **The shape is pinned** in `scripts/brain-shape.json`: every file in one layer (router, playbook, rule,
  model), the caps on each file and each layer, the known duplicate passages. **Changing that file is
  Eric's call.**
- **One home per lesson:** two files sharing a nine-word passage fail unless the pair is pinned, and a
  pinned count may only fall. Merge into one home and point at it.
- **A source on every new block:** `<!-- src: what taught it, YYYY-MM-DD -->` on each line or block added
  since `sourcesSince`.
- **Nothing ships without Eric:** the npm publish of shared refuses a skill or shape commit he has not
  approved (`scripts/brain-review.mjs --check`), and the plugins carry only the approved commit's skills
  (`build-plugins.mjs`). The same script builds his review page; `--approve` takes his exported decisions,
  refuses while a held commit is not reverted, and runs `scripts/brain-eval/gate.mjs`: the candidate against
  a build of the approved brain in the same batch, tied to each build by its brain hash, rejecting a case
  sign test the candidate loses or a craft mean that falls. Only then does the approved commit move.
  How to run the evals: `scripts/brain-eval/README.md`.
- **My brain**, the user's own files in `~/.slates/my-brain`, lays over the bundled skills on their
  machine: a file named like a shared guide adds to it in the guide op, prompts and resources (their file
  first, as the rules that win where they differ, then the shared guide, so a later shared fix still reaches
  them), a new name adds a guide, and the router, its aliases and the `my-brain` topic stay shared. Every
  load holds each file to the shape in `src/skills/brain-check.ts` (a summary, the `caps.mine` caps from
  `brain-shape.json`, embedded at build, and one home per lesson among their files and against every bundled
  skill); a file that fails, or is unreadable, is skipped and named in the preload. 60 days unused, by the
  later of last load and last edit, archives a file, run at MCP server start at most once a day.
  `src/skills/my-brain.ts`; `brain-lint.mjs --root <dir> --mine` runs the same checks plus the summary's
  shape and a source on every block.

1. Drop a markdown file with frontmatter into `slates-api/brain/` (only the router lives here), with an operative summary under its title, and name it in the router (`slates-start-here`) or in a playbook the router names. Pin it in `brain-shape.json` (Eric's yes), give it a tier in `brain/tiers.json` if it is not a license file, and source it.
2. Use portable `name:` and `description:` frontmatter. The shared `src/skills/metadata.ts` parser validates it before embedding or installation. Descriptions distinguish when to use the skill; detailed craft belongs in the body.
3. Rebuild — `scripts/embed-skills.mjs` runs as shared's prebuild and regenerates `src/skills/content.ts` (the `SKILLS` record: the card and router only). The CLI's `install-skills` and the `slates_get_prompting_guide` op read `brainFiles()` (`src/skills/served.ts`), which adds the served brain; never edit the generated file by hand.
4. **🚨 A first-party prompt guide is authority on the MODEL; the ENDPOINT SCHEMA is authority on the
   REQUEST — and the skill has to serve the request** (learned on MiniMax H3, 2026-08-27). MiniMax's
   own guides document an angle-bracket tag block (`<Subject N>` / `<Picture N>` / `<Video N>` /
   `<Audio N>`) as the way to declare references. fal — the provider we actually call — exposes
   references as TYPED SLOTS and its `prompt` description instructs *"refer to reference assets by
   their modality and order: Image 1, Image 2, Video 1, Audio 1"*. Writing the skill from the
   first-party guide alone would have shipped a syntax that reaches the model as literal angle
   brackets. **Read the live OpenAPI before writing a per-model skill, not just the model card.**
   The same read found `prompt_expansion_mode` defaulting to `balanced` — a provider-side prompt
   rewrite that the desktop now disables on every request (prompt-transparency invariant), which is
   itself a fact the skill has to teach.
5. Categories — keep them separate:
   - **Workflow skills** (`slates-one-prompt-film`, `slates-direct-response-ad`, `slates-storyboard-from-script`, etc.) compose multiple ops into a recipe. **No count is stated here on purpose** — this line said "cap ~6, currently AT the cap (6)" while eighteen shipped, which is the shape of claim that reads as a rule and is only ever a stale tally. The real constraint is DISCRIMINABILITY: a new workflow skill has to be one an LLM can tell apart from every existing one by its first sentence alone. If you cannot write that sentence, it is a section of an existing skill.
   - **Per-model prompting skills** (`slates-prompting-nano-banana-2-1`, `slates-prompting-seedance-2-5`, etc.) fire when calling the matching `slates_generate_*` op. Naming convention: `slates-prompting-{model}.md`. One per model variant family. The audio lane adds three: `slates-prompting-seed-audio`, `slates-prompting-elevenlabs` (Sound Effects v2 only — the ElevenLabs TTS surface was removed 2026-08-01) and `slates-prompting-inworld-tts` (the voice seat, added 2026-09-05; `tts` / `voiceover` / `voice` alias to it, `dialogue` stays on Seed Audio). ⚠️ In `resolveGuideTopic()` the `seed-audio` alias MUST be tested **before** `seedance` — "seed-audio" also starts with "seed", and falling through hands the video guide to an audio model.
   - **Per-style prompting** (`slates-style-prompting`) — cross-model style depth (photoreal/anime/painterly/3d-render on Seedance vs Kling vs Nano Banana). Fires on style requests; style names alias to it in `resolveGuideTopic()`. SSOT: born in second-brain `research/style-prompting-research.md`, encoded here — never author style content directly in this file.
   - **Cross-cutting hygiene skills** (`slates-cost-discipline`) fire on every generation call regardless of model. Should be rare — only add when a discipline applies across many ops.
6. If the skill maps to a model id, extend the alias table in `resolveGuideTopic()` (operations/index.ts) so `slates_get_prompting_guide` resolves the model id to it.
